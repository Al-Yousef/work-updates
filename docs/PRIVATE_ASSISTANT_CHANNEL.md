# Private iPhone assistant channel

This #29 implementation supports questions from one explicitly granted owner device. On the desktop assistant, `/channels open` opens a private grant window. Choose an assigned private network address, name your own device, set a finite one-to-thirty-day duration, and confirm that this device may use your private task context and pinned notes. Only then is a separate `wua1:` code created. Paste it into the native iPhone Assistant screen. A private-network connection to the original computer is required; the host remains local and no cloud relay is provisioned.

The new code is a bearer credential for this one private channel, not a verified third-party identity. Anyone holding it can ask questions with the context you granted. It must not be used for group chats, shared devices or another participant. Revocation, expiry, unavailable encryption and global work/privacy holds refuse new requests; revocation also closes only that channel's active answer provider. Ordinary task-pairing codes cannot read assistant history or send assistant questions, and assistant codes cannot control the task queue. Both clients pin the original private endpoint's exact certificate before sending a credential; redirects are refused.

Each channel retains its own bounded assistant conversation and acceptance receipts. Shared context includes the current local task snapshot, explicit pinned notes, commitments and the configured presentation identity. Desktop and other channel conversations are not copied. Source text remains evidence, never permission. This channel exposes no task actions, slash controls, attachments, arbitrary tools or outbound contact. Slack, Teams, SMS and telephone adapters remain unsupported; see the separate [API assessment](CHANNEL_API_ASSESSMENT.md).

Before sending, iPhone saves one exact message identity and text. An HTTP acknowledgement means acceptance, not a completed answer. A separate receiver receipt must match the channel, host, message identity and text hash before pending text is cleared. If acceptance is uncertain, the saved identity is checked again on reconnect and is never resent automatically. Restart converts an interrupted attempt to unconfirmed; a missing receipt remains unknown. The per-phone journal is bounded to 32 pending channels, 512 receipt hashes and 256 KiB, uses iOS complete file protection and is excluded from backup. Changed, redirected, corrupt or future journals hold sending and preserve the original. This first version saves attempted questions; unsent composer edits are temporary.

The host's OS-encrypted grant file stores token hashes, not codes, and is bounded to 32 grants and 256 KiB. OS encryption must be available, with no plaintext fallback. Each separate conversation uses the existing 500-exchange assistant limit, bounded recalled context and 2,000 replay receipts. Model requests use the existing Codex provider and shared resource ledger; a question is an inference request using the owner's configured quota. Grant creation does not itself run inference. Provider sessions remain private and have no execution tools.

The one-time displayed code is transient and disappears when its window closes. iPhone stores its separate credential in a device-only, when-unlocked Keychain entry. Forgetting that phone credential preserves its uncertain questions and receipt checks; it does not revoke the host grant. Revoke access on the original desktop when the device or recipient changes. The desktop window can separately clear an idle selected channel conversation, including a revoked one. Clearing retains replay receipts and leaves other channels and original source chats unchanged.

Synthetic tests exercise actual host routing, encrypted grants, durable acceptance, history separation, restart, deduplication, expiry and revocation. GitHub CI compiles the native iPhone candidate, checks pinned TLS against an owned synthetic host and exercises the native assistant sheet. The unsigned Simulator interaction uses an explicitly injected disposable credential store in a Debug integration fixture; normal/release builds always use Keychain and refuse its failures. Keychain availability in a correctly signed physical build is separate evidence. Isolated desktop CI checks the actual sandboxed grant window and its consent/revocation/reset behavior. These checks do not establish physical iPhone delivery, background networking, actual account inference, supported third-party channels or task-action parity. Those remaining #29 acceptance items stay open.
